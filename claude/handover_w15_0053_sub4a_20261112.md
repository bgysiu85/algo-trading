# W15-0053 sub 4a · Core live exit manager: handover (2026-11-12, Build & test chat, Opus)

## In plain terms
The core of the exit manager is built and tested against a **fake** IBKR session only. When a futures fill from IBKR Mobile / web arrives, it places a protective stop at IBKR (MCL: fill − $0.60 long, + $0.60 short), keeps the stop's size equal to the position as Ben adds or trims, cancels the stop at once when the position goes flat, and at 16:55 New York sends a market exit (in the same OCA group as the stop) and cancels the stop only once that exit is working. It is **dry by default**: it logs every order it would send and sends none. Paper needs `XM_MODE=paper` **and** `XM_ACCOUNT=DU...` matching the connected account; there is no live mode, and live ports are refused. **Nothing was run against IBKR; nothing logged in.**

## How each rail is met (test class in `test_rails.py`)
1. **Reduce-only** (`TestRail01`): fresh `reqPositions` + `reqAllOpenOrders` before every send; side must be opposite the position (flat = refused); order qty + every other exit-side working order (any client) ≤ position; an OCA group counts once at its largest member. The stop is sized `min(tracked fills, what the broker position allows)`, and retries until the broker catches up.
2. **One exit** (`TestRail02`): `orderRef XM:<localSymbol>:<execId>`, OCA `XMOCA:<localSymbol>:<execId>`, ocaType 1, GTC. Second stop refused; the only second order allowed is one market exit in the same OCA group.
3. **Stop first** (`TestRail03`): first order after the fill is the stop; latency fill-event → send logged (`stop_latency`), > 3 s alerts; MCL/CL ± $0.60; MNQ mode A uses `atr_provider` (4b), until then fixed mode B 250 pts with an `EMERGENCY_FALLBACK` alert.
4. **Never loosens** (`TestRail04`): long up only, short down only; refusals logged with old/new.
5. **Other apps** (`TestRail05`): another app's exit order on the trade at the fill → OBSERVE-ONLY, nothing placed; one appearing later → ours cancelled, OBSERVE-ONLY; if it then disappears → `OBSERVE_UNPROTECTED` alert. NAS trader (17) orders do not trigger this but do count in rail 1.
6. **Partials / reconcile** (`TestRail06`): stop qty follows every execution; reconcile every 15 s (config ≤ 30), on every position event (within 1 s) and on reconnect; each reconcile also reads `reqExecutions`, so a fill whose event never reached client 31 is still picked up.
7. **Unsafe contract** (`TestRail07`): root not in table, root switched off (CL, ES, MES, NQ), contract details ≠ table, ≤ 2 trading days to last trade date, non-futures → alert only, no orders.
8. **Over cap** (`TestRail08`): still protected, `RAIL8` alert, no 16:55 flat.
9. **Kill switches** (`TestRail09`): PAUSE, FLATTEN, STOP_MANAGER, runaway guard; all leave the resting stop (FLATTEN replaces it with the exit).
10. **Paper lock** (`TestRail10`, `test_run_manager.py`): every reported account must start with D; paper needs the configured DU account; live port refused before connecting; dry connects read-only and never calls `placeOrder` / `cancelOrder`.
11. **Flat cancels** (`TestRail11`): manual flatten cancels in the same loop pass; flat seen only in positions → `FLAT_UNSEEN` + cancel; reversal → old stop cancelled, new opposite stop; a shrinking position shrinks the stop at once.
12. **Stale data** (`TestRail12`): no tick for 30 s in session → alert, rule actions blocked for that contract, stop untouched. Tick level only; the bar-level check is 4b.
13. **Maintenance / restarts** (`TestRail13`): no rule action 17:00–18:00 NY or at the weekend; restart resumes from `state.json` and re-binds its own stop by orderRef (no duplicate); a position held before start, or one the tracked fills cannot explain for > 5 s (NAS trader fill, a change underneath), → ALERT-ONLY.
14. **Log** (`TestRail14`): every fill, send / would-send / modify / cancel with reason, broker qty and exit load, refusals with rail number, alerts, latencies, code + config hash; append-only across restarts.

## Decisions I made in 4a (please confirm or change; each is one setting or a few lines)
1. **PAUSE does not stop protection.** PAUSE blocks rule actions (16:55 flat, 4b rule exits) and stop-level changes. A new fill while paused still gets its stop, and the stop qty still follows the position. Reason: "paused" should never mean "unprotected". The runaway guard is stricter: once tripped it blocks every send until restart (cancels always allowed).
2. **FLATTEN puts the exit first, then cancels the stop**, the same as the 16:55 flat. The registration (rail 9b) lists "cancel, then market out"; I used the plan's never-unprotected order. OCA type 1 stops both filling.
3. **ALERT-ONLY sticks until the position is flat**, even if the numbers match again later.
4. **Over-cap positions are not flattened at 16:55** (rail 8 says "no other action"); they are held overnight on the stop with an alert. Ben may prefer flattening them.
5. **A failed 16:55 exit is not retried**; alert, the stop stays.
6. **Stale data does not block the 16:55 flat** (it is a clock rule, not a bar rule).
7. **Non-CL emergency mode A falls back to fixed mode B** (MNQ 250 pts) until 4b supplies the ATR.
8. In dry mode the virtual stop is not saved in `state.json`; after a restart the dry log shows a `STOP_MISSING` alert and a re-placed virtual stop.
9. Exchange holidays and early closes are not modelled (at worst a stale-data alert on a holiday).

## NOT verified (only real IBKR can show these; sub 5)
- **Whether fills from IBKR Mobile / web reach client 31 at all**, either as `execDetailsEvent` or through `reqExecutions` (IBKR normally sends other clients' executions only to the master client). If neither does, every manual trade shows up only as a position change, goes ALERT-ONLY and gets **no stop**. **This is the first thing sub 5 must check.**
- Whether `reqAllOpenOrders` from client 31 shows orders placed in IBKR Mobile / web (rail 5 depends on it).
- **Reduce-only:** no attribute is set; I know of no reduce-only flag on IBKR futures orders. Rails 1 and 11 are the only guard; the stale-stop window after a manual flatten (one loop pass plus the cancel round trip) is the main residual risk.
- That IBKR Mobile / web can stay logged in beside the NAS Gateway on the same paper username.
- OCA type 1 with a resting STP and a MKT on CME/NYMEX futures (overfill protection), GTC + `outsideRth=True` stops triggering overnight, orderRef / OCA name length (about 35 characters), modifying a stop by orderId after a Gateway restart.
- Time taken by the fresh `reqPositions` + `reqAllOpenOrders` before each send (counts towards the 1 s target), and whether position updates lag fills.
- Market-data permission for MCL / MNQ on the paper login (without it, a RAIL12 alert 30 s after every fill).
- Paper ports allowed: 4002, 4004, 7497. Inside the Gateway's network the right one is 4002 (the default), as for the trader.
